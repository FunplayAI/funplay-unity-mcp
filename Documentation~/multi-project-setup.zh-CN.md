# 同时开多个 Unity 工程

*[English](multi-project-setup.md)*

打开两个不同工程的 Unity 编辑器，可以同时对外提供 MCP 服务。每个工程有自己的端口和自己在 AI
客户端配置里的条目，因此一次工具调用只可能落到它本该去的那个编辑器上。

本文说明默认行为、MCP Server 窗口里的各项控件，以及哪些情况需要你做一次决定。

---

## 快速开始

**新工程**无需任何配置：

1. 分别打开两个工程的 Unity，进入 **Funplay > MCP Server**，勾选 **Enable MCP Server**。
2. 各点一次 **Configure**（先在下拉里选好客户端）。
3. 重启 AI 客户端。

此时客户端配置里每个工程各一条：

```json
"funplay-game-alpha": { "url": "http://127.0.0.1:24312/" },
"funplay-game-beta":  { "url": "http://127.0.0.1:21874/" }
```

在按 server 给工具加命名空间的客户端里，工具名会变成 `mcp__funplay-game-alpha__execute_code` 和
`mcp__funplay-game-beta__execute_code` —— 发错编辑器这件事从"需要小心"变成"结构上不可能"。

> **从旧版本升级？** 端口不会动：工程会保留原本在用的端口，已配置好的客户端照旧可用。见
> [从旧版本升级](#从旧版本升级)。

---

## 端口是怎么定的

每次启动服务器时的解析顺序：

1. **你 pin 过的端口**永远优先。
2. 否则**按工程路径派生**：对归一化后的路径取 SHA-256，映射到 **20000–29999**。这个区间在
   8000–9000 那段拥挤的开发工具端口之上，又在操作系统分配出站连接的临时端口段之下
   （macOS 49152+、Linux 32768+）。
3. 如果解析出的端口**被别的进程占着**，服务器会改绑附近一个空闲端口，在控制台告警，并汇报它
   实际绑上的端口。

派生是路径的纯函数，因此同一工程每次启动都是同一个端口 —— 这正是写进客户端配置的地址能长期
有效的原因。除非你 pin，端口相关的东西不会落盘。

### 关于回退端口

回退端口**故意不落盘**：真正的端口每次启动都会重新派生，而存下来的回退值会比造成它的那次冲突
活得更久。它只在本次编辑器会话内被记住，换来两个好处：

- 域重载之后，对于已知被别人占着的端口，不再重新等满约 10 秒的重试窗口。
- 会优先重新绑上同一个回退端口，因此连在它上面的客户端能扛过重编译。

回退生效期间，**一键配置会被阻止**。写入被占用的稳定端口，可能把本工程的修改调用发给占着端口的
另一个进程；写入临时回退端口，则会在重启后留下失效条目。已有客户端条目若仍指向被占用的稳定端口，
也可能连到那个进程，因此冲突解决前不要继续使用。点 **Use Per-Project Port** 或 **Pin Current Port**，
等服务器重启完成后，再重跑配置。

## 条目名是怎么定的

条目名是 `funplay-<工程目录名>` —— 例如工程在 `~/work/game-alpha`，条目名就是 `funplay-game-alpha`。
非 ASCII 字母数字的字符连成一段折叠为一个 `-`，但**不会拆 camelCase**：`~/work/GameAlpha` 会得到
`funplay-gamealpha`。

- 用的是**工程目录名**而不是 `Application.productName`：产品名常常没改过（还是 Unity 的默认值）
  或者填的是中文。
- 只保留 ASCII 字母和数字，其余字符折叠成 `-`。客户端工具名的合法字符集是 `[a-zA-Z0-9_-]`，
  超出这个集合会生成客户端直接拒绝的工具名。如果过滤后什么都不剩（比如目录名全是中文），
  会退回到一小段工程哈希，例如 `funplay-a3f9c1`。
- 名字会被截断，以保证 `mcp__<条目名>__<工具名>` 不超过客户端对工具名的 64 字符上限。

### 两个工程目录名相同

它们会解析出同一个条目名。你后配置的那个工程会发现这个名字已经被"不是自己"的工程占了
（它没有写过这条的记录），于是**自动追加一小段工程哈希**：

```json
"funplay-client":        { "url": "http://127.0.0.1:24312/" }
"funplay-client-a3f9c1": { "url": "http://127.0.0.1:21874/" }
```

谁都不会被覆盖，也没有需要你去打开的开关。客户端配置面板会说明它加了哈希，那段后缀不会莫名
出现。

## MCP Server 窗口

| 控件 | 作用 |
| --- | --- |
| **Server Port** | 显示本工程当前实际在用的端口。填一个值就是 pin；清空则释放 pin。 |
| **Pin Current Port** | 把框里显示的端口 pin 住。之所以需要这个按钮：重复输入框里已有的值不会触发提交。 |
| **Use Per-Project Port** | 释放 pin，回到派生端口。仅在已 pin 时显示。 |
| 输入框下面那行小字 | 说明端口的来源：pin 的、派生的，还是因为解析出的端口被占而落在回退端口上。 |

客户端配置面板会显示它将写入的条目（`Entry: funplay-game-alpha -> http://127.0.0.1:24312/`），
并说明自动追加的工程哈希。处于回退绑定时，预览会替换为安全阻止原因与两种恢复方式。

## 两种 Transport Mode 都支持

按工程分配端口对 **Direct HTTP** 和 **Broker Mode（实验性）**同样生效 —— 两者用的是同一套端口
解析逻辑，而且切换模式不会改变端口和条目名，所以切换时不需要重跑配置。

| | Direct HTTP | Broker Mode |
| --- | --- | --- |
| 每工程独有的东西 | 监听端口 | 端口，外加 `<工程>/Library/FunplayMcp/Broker/`（pid 文件与编译好的 broker）——都在工程目录内，天然隔离 |
| 撞端口时 | 会话内记住这次冲突：缩短重试，并优先重试上次那个回退端口 | 请求的端口仍被占着时，**保留**已经健康运行在回退端口上的 broker，而不是杀掉重起 |
| 写进客户端配置的 | 稳定端口；回退期间阻止配置 | 稳定端口；回退期间阻止配置 |

broker 内部是单租户的（单队列、单个等待中的后端），但这在这里不构成限制：**每个工程各自运行
一个 broker 进程**，各占一个端口。

## 从旧版本升级

已经有 `UserSettings/FunplayMcpSettings.json` 的工程，说明它本来就在某个端口上服务、客户端也已
按它配好，因此升级会**把那个端口记为 pin，什么都不动**：不用重跑配置，条目名不变，工具名不变。

也就是说，按工程派生只是**新工程**的默认值。要让一个老工程也用上，做三步：

1. **Funplay > MCP Server** → 点 **Use Per-Project Port**。
2. 点 **Configure**。
3. 重启 AI 客户端。

动手前先知道两个后果：

- 条目名会从原来的名字（通常是共享的 `funplay`）改成 `funplay-<目录名>`，因此**工具名前缀会变**。
  文档、权限白名单、hooks 里凡是按旧前缀匹配的都要跟着改。
- 遗留的共享 `funplay` 条目**不会被自动删除** —— 机器上任何一个工程都可能写过它，删不删不该由
  插件替你决定。客户端配置面板会提示它还在；等所有工程都配置过之后手动删掉即可。

团队注意：`UserSettings/FunplayMcpSettings.json` 是每台机器一份、通常被 git 忽略，所以每位
同事都会各自经历这一次。

## 场景速查

| 情况 | 怎么做 |
| --- | --- |
| CI，或防火墙只开一个端口 | 在 **Server Port** 里 pin 那个端口。pin 永远优先于派生，且不会漂移。 |
| 两个工程目录名相同 | 什么都不用做 —— 后配置的那个会自动追加工程哈希。 |
| 派生端口被无关进程占了 | 什么都不用做 —— 服务器会绑附近的空闲端口并告警。冲突是永久的就 pin 一个端口。 |
| 两个升级来的老工程仍在抢同一端口 | 在其中一个里点 **Use Per-Project Port**，然后重跑一次该客户端的配置。 |
| Broker Mode（实验性） | 无需额外设置。broker 的 pid 文件本来就按工程隔离，且跟随同一个解析端口。 |
| 移动或重命名了工程目录 | 派生端口和条目名都会变（两者都来自路径）。重跑 **Configure** 并删掉旧条目。 |

## 排查

**升级或改端口后客户端连不上。** 客户端配置还指着旧端口。打开 MCP Server 窗口，看条目那行显示
的地址，点 **Configure**，然后重启客户端。

**客户端里某个 server 显示连接失败。** 大概率是遗留的 `funplay` 条目 —— 现在已经没有任何工程会
写它。手动删除即可。

**看实际在监听什么：**

```bash
lsof -nP -iTCP -sTCP:LISTEN | grep -E ':(2[0-9]{4}|8765)'
```

**直接探活某个端口：**

```bash
curl -s -m 5 -X POST http://127.0.0.1:24312/mcp -H 'Content-Type: application/json' \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}'
```

**自己算某个工程的派生端口**（归一化路径 = 完整路径、去掉结尾分隔符、转小写）：

```bash
python3 -c "import hashlib,sys; p=sys.argv[1].rstrip('/').lower(); print(20000+int(hashlib.sha256(p.encode()).hexdigest()[:8],16)%10000)" /path/to/UnityProject
```

**`UserSettings/FunplayMcpSettings.json` 里值得一看的字段：**

| 字段 | 含义 |
| --- | --- |
| `port` / `portConfigured` | pin 的端口，以及 pin 是否生效。`portConfigured: false` 时存的 `port` 不参与解析，走派生端口。 |
| `mcpLastClientConfigKeys` | 本工程上次写入的条目名，按客户端目标分别记录。这是判断"某条条目是不是自己的"的唯一证据，靠它才能在改名后只回收自己那条、不碰别的工程。 |
| `settingsVersion` | 配置结构版本；上面那次一次性升级迁移由它驱动。 |

当前实际端口以窗口显示为准；文件里记的只是"选了什么"。

## 不支持的做法

- **多个编辑器共用一个端口。** 每个编辑器各自持有一个端口。"单端点 + 运行时选实例"是另一种
  设计，而当前这套刻意不引入"现在是哪个编辑器"这种客户端可能弄错的状态。
- **同一个工程目录开两次。** Unity 本身就不允许。ParrelSync / MPPM 的克隆各自在独立目录里，
  因此天然派生出各自的端口。
- **跨机器访问编辑器。** 本文涉及的一切都仅限 loopback。
